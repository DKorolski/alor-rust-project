# Live Incident Note: `sessiongap` timed exit blocked by control-path recycle timeout

Date: 2026-03-31  
Deployment line:
- gateway image: `ghcr.io/dkorolski/alor-rust-project/alor-gateway:dev-774b917-diag-20260326`
- runtime image: `ghcr.io/dkorolski/alor-rust-project/strategy-runtime:dev-a1ee034`
- runtime config: `/configs/runtime.sessiongap.live.7502MIW.toml`
- gateway config: `/configs/gateway.sessiongap.live.7502MIW.toml`

## 1. Executive Summary

On 2026-03-31, the live `sessiongap` stack entered a real `USDRUBF` position successfully and later attempted a scheduled time-based exit.

The exit did not reach the broker. Instead:

- gateway detected a stale control path;
- gateway started a recycle / fresh-session recovery attempt;
- the recycle did not complete before the configured timeout;
- the exit send was blocked;
- runtime received `control_path_recycle_failed`;
- strategy transitioned `PendingExit -> Blocked`;
- the broker position remained open until manual operator intervention.

Operator action:

- `sessiongap` automation was stopped;
- the position was manually flattened at `2026-03-31 23:44:24 MSK`;
- operator confirmed there were no active orders after the manual close.

This incident is important because it is the clearest live proof so far that the currently deployed hardening path can be invoked on a natural `sessiongap` order flow and can fail operationally via recycle timeout.

## 2. High-Level Reading

What happened is not the earlier `create:limit -> protocol_reset_without_close_handshake` failure class.

This time the sequence was:

1. live strategy entry succeeded normally;
2. position remained open into the scheduled exit window;
3. exit intent was generated by runtime;
4. gateway classified the control path as stale;
5. gateway attempted recycle-before-send;
6. the fresh CWS session was not ready before timeout;
7. gateway refused to send the exit order;
8. runtime blocked;
9. manual flatten was required.

So the new incident is not "we lost observability on a transport reset".  
It is "hardening engaged, but the protective path timed out and prevented automatic flatten".

## 3. Chronology

### 3.1 Successful entry earlier in the session

Observed on 2026-03-31:

- `sessiongap` emitted a natural live entry intent;
- gateway sent `opcode="create:limit"`;
- the request was accepted and filled;
- resulting broker position became:
  - `USDRUBF qty = 1.0`
  - `avg_price = 81.74`
- runtime transitioned into `InPosition`.

This matters because it confirms the strategy was operating normally before the exit problem.

### 3.2 Timed exit intent

At approximately `2026-03-31 23:30:07 MSK` (`2026-03-31 20:30:07 UTC`), runtime attempted the scheduled session exit.

Observed in runtime:

- `live phase transition` `InPosition -> PendingExit`
- `intent_emitted action="place"`
- request id:
  - `36c9fe78-70db-5fdc-a0de-abf833a94f0c`

This was a real strategy-generated exit, not a manual probe.

### 3.3 Gateway hardening path engaged

Observed in gateway around the same exit attempt:

- `control_path_stale_detected`
- `control_path_recycle_start`
- recycle / fresh-session recovery requested on CWS

The gateway therefore did not blindly send the exit order over a stale control path.  
It first tried to establish a fresh CWS session.

### 3.4 Recycle timeout and blocked send

At approximately `2026-03-31 23:30:12 MSK` (`2026-03-31 20:30:12 UTC`), the recovery attempt failed to become ready in time.

Observed failure:

- `error_code = "control_path_recycle_failed"`
- `error_msg = "fresh cws session was not ready before recycle timeout"`

Observed consequence:

- exit send was blocked instead of sent late over an uncertain control path.

### 3.5 Runtime blocked state

Observed in runtime after the failed recycle:

- `command rejected`
- `PendingExit -> Blocked`
- blocked reason:
  - `ack_failed:Error`

At that point the strategy no longer had an autonomous clean path to flatten the still-open live position.

## 4. Broker / State Evidence

After the failed timed exit, VPS inspection showed:

- broker position still open:
  - `USDRUBF qty = 1.0`
  - `avg_price = 81.74`
- no new working exit order visible;
- `runtime.state.session_gap_standalone.live.7502MIW` reflected blocked strategy state.

This is the key operational point:

- hardening did not lead to a bad duplicate send;
- but it also did not produce a successful safe flatten;
- the system remained in a live-risk state until operator action.

## 5. Operator Mitigation

Because the position remained live while strategy state was blocked:

- `sessiongap` automation was stopped on the VPS;
- the operator manually flattened the broker position at:
  - `2026-03-31 23:44:24 MSK`
- operator confirmed no active orders remained after the manual close;
- VPS verification after the stop showed no running `sessiongap` containers.

This removed the immediate operational risk.

## 6. What This Incident Proves

Confirmed by this incident:

- the live `sessiongap` path can emit real `Place` intents on the deployed line;
- the currently deployed hardening path is not merely theoretical; it can engage on natural runtime flow;
- the gateway can correctly refuse to send over a stale path;
- the current recycle timeout / readiness contract can still leave a live position unflattened;
- operator intervention is currently required when this specific failure path occurs.

## 7. What Remains Open

This incident leaves several engineering questions open:

1. Should exit / flatten intents be allowed to use a different degraded-mode policy than entry intents?
2. Is the current recycle timeout too short for live recovery under this contour?
3. Is the readiness condition for "fresh CWS session ready" too strict for the intended exit path?
4. Should there be an automatic post-failure fallback for flatten-only safety cases?
5. Should runtime remain `Blocked`, or should there be an explicit close-only recovery lane after `control_path_recycle_failed` on exit?

## 8. Operational Conclusion

Recommended reading of the incident:

- the protective hardening layer did engage;
- it prevented an unsafe stale-path send;
- but the current behavior is still not operationally sufficient for unattended live exit safety.

Short form:

- entry succeeded;
- scheduled exit triggered hardening;
- recycle timed out;
- exit did not reach broker;
- position stayed open;
- operator manually flattened;
- `sessiongap` was left stopped after the incident.

## 9. Recommended Follow-Up

- preserve this incident as the reference case for `control_path_recycle_failed` on a live natural strategy exit;
- treat it separately from the older `protocol_reset_without_close_handshake` incident class;
- review timeout and fallback semantics specifically for flatten / risk-reducing orders;
- do not resume unattended `sessiongap` live operation until the team agrees on the recovery policy for this path.
